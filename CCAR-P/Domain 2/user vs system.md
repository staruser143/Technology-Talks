Good clarifying question, and it matters for the exam because it connects directly to the caching material. Templates apply to **both**, but the way they're used — and what it means for caching — is different in each case.

**System prompt templates** — these are templated at the *deployment/configuration* level, not per-request. Example: a base system prompt structure with slots for role, domain instructions, and tool list, filled in once when a feature is configured (e.g., the same underlying template producing slightly different system prompts for "customer support bot for Product A" vs. "Product B," but each one is fixed once deployed). Once filled, this becomes the *stable* content of a given deployment — it doesn't change from request to request within that deployment, which is exactly why it's the part that belongs at the front of the prompt for caching purposes.

**User message templates** — this is the more common, classic case: a reusable instruction structure with variable slots filled in *per request* — e.g., `"Classify the following email as spam or not spam: {email_text}"`. Here the template structure is fixed, but the filled-in content (`{email_text}`) is different on every single call. This is inherently the *dynamic* part of the prompt.

**Why the distinction matters for the exam, tying back to caching**: this maps directly onto the stable-vs-dynamic split from Sample Question 2. System-prompt-level templates, once instantiated for a given deployment, are exactly the kind of content that should sit in the cacheable prefix — reused, unchanged, across many requests. User-message templates are expected to vary every request by design, so they belong *after* the cached prefix, never inside it. A common exam trap is a design that re-templates or re-generates part of the "system" content per request (e.g., dynamically inserting request-specific data into what's supposed to be the stable system prompt) — that breaks the cacheable prefix even though it's technically still "in the system prompt," because caching requires the prefix to be byte-identical across calls.

So the practical rule: **template the system prompt for reuse across a deployment; template the user message for reuse across requests within that deployment** — and keep the two cleanly separated so the stable one stays genuinely stable.
