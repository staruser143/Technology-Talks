Regarding the tools which are needed when adding them as part of system prompt, is there a way to load them dynamically when required for a subagent instead of loading then all at Start and increase context when they would not be actually used


Yes — this is real, has a name, and works exactly the way you're describing. Confirmed:

**Tool Search** is the exact mechanism. Instead of loading every connected tool's full schema into context upfront, the agent (or subagent) receives only a lightweight summary of what's available, and searches/loads the specific tools it actually needs, on demand, when a task calls for a capability not already loaded. This is enabled **by default** in current SDK versions.

**Why it exists — the two problems it directly solves, both things you've already reasoned through:**
1. **Context efficiency**: tool definitions can eat real space — roughly 10-20K tokens for just 50 tools loaded the naive way. Withholding full schemas until actually needed avoids paying that cost for capabilities a given task never touches, which is the exact "MCP servers eating 34% of the window for tools you never used" problem from your last scenario, just generalized as a built-in mechanism rather than something you have to notice and fix manually via `/context`.
2. **Selection accuracy**: this is the concrete evidence you already know — tool selection accuracy measurably degrades once you're loading more than roughly 30-50 tools at once. Tool Search fixes this the same way progressive discovery fixed it in your Domain 3 material: fewer, more relevant options in context at decision time, rather than the model having to sort through everything available.

**How it applies specifically to subagents**: this connects directly to the earlier "how does a subagent get its tools" discussion. A subagent can be scoped with a restricted tool list at definition time (e.g., `tools: ['Read', 'Grep', 'Glob']`), and independently, Tool Search governs *how* those (or a larger connected set) actually get loaded into that subagent's isolated context — rather than all of a subagent's available tool schemas being dumped in at spawn time regardless of whether the specific subtask needs them, only the 3-5 most relevant get pulled in as the subagent's work actually calls for them.

**One mechanical detail worth knowing, since it ties back to compaction**: if a subagent's session runs long enough that its own context gets compacted, previously-discovered tools can get dropped from context in that compaction pass — and the agent simply searches and reloads them again if needed afterward. This is a nice, low-stakes example of "compaction dropping something, but it's fine because it's cheaply recoverable" — a useful contrast to your mental-health scenario, where what got dropped *wasn't* cheaply recoverable. Not everything that compaction might lose needs the structural-protection treatment; it depends on whether losing it is a minor, self-correcting inconvenience (a tool gets re-searched) or a genuine, unrecoverable problem (a safety fact never resurfaces on its own).

**One practical threshold worth flagging**: the docs note that with fewer than roughly 10 tools total, loading everything upfront is typically *faster* than paying the extra round-trip Tool Search's first-time discovery step costs — so this isn't a strictly "always better" default, it's a trade that pays off specifically once you're dealing with enough tools that the context-savings outweighs the search overhead, echoing the same "does this technique's benefit outweigh its own cost, given the actual scale" judgment you've applied to caching, decomposition, and multi-agent orchestration throughout this whole session.
