Excellent catch — and you're right on both counts. Let me correct the scenario properly, because it was architecturally sloppy in a way that matters for the exam.

**On grouping**: yes. What I described — 500 sequential individual synchronous API calls, one ticket at a time, with an artificial delay between each — isn't actually how a well-architected overnight batch job for this use case would be built. Anthropic has a dedicated **Message Batches API** specifically for this: you submit up to 100,000 requests together in one job (a JSONL payload), Anthropic processes them asynchronously, and results come back within 24 hours (often much sooner). A 500-ticket overnight job is exactly the textbook use case — no real-time human waiting, tolerant of delay, high volume. My scenario invented a synchronous-loop architecture with artificial spacing to manufacture the TTL problem, which isn't how this workload should actually be built in practice — good instinct to question it.

**On the discount**: also yes, and it's a real, separate lever from caching, worth knowing distinctly for the exam. The Batches API gives a flat **50% discount on both input and output tokens** compared to the standard synchronous API, unconditionally — no volume threshold to unlock it. And critically, **it stacks with prompt caching rather than replacing it**: cache reads are already priced at roughly 10% of base input cost, and that discount applies on top of the batch discount — so a cached prefix processed through the batch API can end up costing roughly 5% of the standard synchronous, non-cached price. Anthropic has specifically recommended pairing the **1-hour TTL** with batch workloads, since batch jobs can have exactly the kind of variable, sometimes-longer-than-5-minutes processing gaps between related requests that we were just diagnosing.

**So the corrected version of that scenario's premise would be**: the 500 tickets should be submitted together as one Batches API job, each request in the JSONL payload carrying the same `cache_control` marker (ideally with `"ttl": "1h"` given batch processing timing isn't guaranteed to be tight), getting both the 50% batch discount *and* the ~90% cache-read discount stacked together — rather than an artificial sequential-with-delays architecture that manufactures a TTL problem out of a design choice nobody would actually make.
