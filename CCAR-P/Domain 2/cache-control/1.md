Fair catch — you're right, I described the conceptual prompt *ordering* but never actually named the mechanism that makes caching happen. Let's fix that gap, since `cache_control` is the actual API-level lever, not just "put stable stuff first."

**What `cache_control` actually is**

Ordering stable content first is necessary but not sufficient — caching doesn't happen automatically just because your prompt happens to have a stable prefix. You mark a specific point in your request with a `cache_control` parameter, and that marks a **breakpoint**: everything up to and including that block becomes a candidate for caching. On the next request, if that same prefix (up to that breakpoint) is byte-identical to what was cached, you get a cache hit — a cheap read instead of full-price processing.

Key mechanics worth knowing:
- **Prefix order is fixed**: tools, then system prompt, then messages — cache prefixes are built in that hierarchy, each level building on the one before it.
- **Up to 4 explicit breakpoints per request**, if you want to cache different sections independently (useful when some sections change more often than others).
- **You often only need one breakpoint** — placed at the end of your static content — and the system automatically finds the longest matching cached sequence up to that point, checking back up to ~20 content blocks.
- **Automatic caching** exists too for multi-turn conversations, handling breakpoint placement for you as the conversation grows, without you manually managing it turn by turn.

**How this actually applies to the legal-tech scenario**

In the fixed version, the request would look like this at the API level:

```
system: [
  { type: "text", text: "<role instructions + 6,000-token playbook>", cache_control: {"type": "ephemeral"} }
]
messages: [
  { role: "user", content: "Review this clause: <varying clause text>" }
]
```

The `cache_control` marker sits at the end of the system block — that's the breakpoint. Everything up to and including it (the role instructions + playbook) is what gets cached and reused across calls, *provided it's identical every time*. The varying clause lives in the user message, entirely outside the cached region, so it's expected to change freely without breaking anything.

This also makes the timestamp bug concrete: if that timestamp had been placed *inside* the system block, before the `cache_control` marker, it would be part of the cached prefix — and since it changes every call, the block marked for caching would never actually match the previous one byte-for-byte, so the cache would never hit, even though `cache_control` was correctly applied. The marker alone doesn't guarantee a hit — the content up to it still has to be identical. That's the distinction worth holding onto: `cache_control` tells the system *where to look* for a reusable prefix; it doesn't make content stable on its own — you still have to actually keep everything before the breakpoint unchanged.
