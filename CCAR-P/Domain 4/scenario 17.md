**Scenario**

A mortgage company's Claude-powered loan-underwriting assistant has been in production for 10 months. A comprehensive quarterly review surfaces the following:

- **Metric practice**: The team's primary evaluation metric has always been overall approval-decision accuracy against a human-reviewer ground truth set. The system scores 93%. However, a deeper breakdown reveals that of all applications that *should have been flagged* for manual underwriter review due to unusual income patterns (roughly 8% of volume), the system correctly flags only 40% of them — the other 60% get auto-approved or auto-denied incorrectly, but because this category is a small share of total volume, it barely dents the 93% aggregate.

- **Eval set**: The 1,500-application eval set used to validate the system was built from applications processed in the system's first two months of production. Since then, the company has started serving a meaningfully different mix of loan types (a new jumbo-loan product launched 6 months ago now represents 20% of volume) that the eval set has zero examples of.

- **A/B test history**: Three months ago, the team tested a bundled change — a new model tier upgrade *and* a rewritten system prompt *and* three new few-shot examples for edge cases — all at once, against the old combined setup. The bundle won on accuracy and was shipped. Finance now wants to know if the model upgrade specifically is worth its added cost, and the team has no way to isolate that.

- **A recent complaint pattern**: Several denied applicants have disputed their denial reasoning — investigation shows the assistant's denial letters sometimes cite "insufficient employment history documentation" as a reason, referencing a specific document type, when the applicant's file actually contained that exact document type, correctly uploaded and present in the record the assistant had access to.

- **Cost**: Per-application processing cost has risen 40% over 10 months through incremental system-prompt additions (new compliance disclosures, additional few-shot examples added one at a time after various complaints) — never reviewed in aggregate.

**Question**: Which of the following best identifies all the distinct problems present, each correctly matched to its Domain 4 sub-topic?

A) There is one root problem — the model needs to be upgraded to a more capable tier — and this single fix would resolve the metric issue, the eval set issue, the A/B test issue, the denial-letter issue, and the cost issue simultaneously.

B) Five distinct, independently-diagnosable problems: (1) metric selection — overall accuracy is masking poor performance on the manual-review-flagging minority class, the exact category where failure matters most; needs a dedicated recall metric for that class, not just aggregate accuracy. (2) eval set staleness — the eval set predates the jumbo-loan product and has zero coverage of 20% of current volume; needs refreshing with current-era examples. (3) A/B testing — bundling three changes together means the model upgrade's individual contribution can't be isolated now that finance needs that answer; should have been tested as isolated components. (4) diagnosis — the denial-letter issue is a hallucination (a confident, specific claim — the document is missing — that's directly contradicted by what's actually in the applicant's file, not a formatting or reasoning-structure problem), needing a groundedness safeguard tying stated denial reasons to actual file contents, not a model upgrade. **Why B is right — mapping each problem to its exact origin scenario**

1. **Metric selection**: this is your fraud-detection scenario, transplanted into underwriting. 93% overall accuracy is dominated by the large majority of straightforward applications, while the 8% minority needing manual-review flagging — precisely the highest-stakes category, since it's where unusual income patterns could hide either fraud or legitimate cases needing human judgment — gets caught only 40% of the time. The aggregate number is technically accurate and completely misleading about what matters most, exactly the pattern from your fraud scenario: the fix is a dedicated recall metric on that specific minority class, not a better aggregate number.

2. **Eval set staleness**: this is your cybersecurity threat-landscape scenario. The eval set was valid when built (first two months of production) but the world it represents has moved — a new loan product now representing a full fifth of volume has zero representation in what's being used to validate the system. A consistent, unchanging eval score against this stale set tells you nothing about jumbo-loan performance specifically, the same blind spot as the security eval never catching novel attack patterns.

3. **A/B testing / bundled changes**: this is directly your financial-advisory bundled-changes scenario. Testing model-upgrade + prompt-rewrite + few-shot-additions together as one variant meant the win was real but unattributable — and now, exactly as in that scenario, a real business question (is the model upgrade worth its cost) has arrived with no data to answer it, because isolation was never built into the original test design.

4. **Diagnosis — hallucination, not prompt failure or model mismmatch**: this is the sharpest diagnostic test in the compound scenario, and worth being precise about why it's hallucination specifically and not the other two categories. Apply the test from your diagnostic deep dive: is the *content* the problem, or the *structure*? The denial letters are structurally fine — properly formatted, citing a real, valid *reason category* ("insufficient employment history documentation"). What's wrong is a specific, confident factual claim — that this document is missing — directly contradicted by what's actually present in the applicant's own file. That's the hallucination signature exactly: confident, plausible-sounding, specific content not grounded in what the model was actually given access to, echoing your 10-K risk-factors scenario (a confident claim about document content that traces to nothing real in the source). It's not prompt failure (nothing about format or missing reasoning steps is at issue), and it's not model mismatch (there's no indication this requires deeper reasoning capability — it requires the model to actually check the file rather than assert a claim about it). The fix is a groundedness safeguard tying stated denial reasons to a verified check against actual file contents, not a capability upgrade.

5. **Cost accumulation**: this is your customer-support system-prompt-bloat scenario exactly — 40% cost rise over 10 months through individually-reasonable additions (new compliance disclosures, few-shot examples added one at a time), never audited in aggregate. Same mechanism, same fix: periodic token/cost review treating the current state as something to re-verify, not a launch-time decision that stays valid indefinitely.

**Why the others are wrong**

- **A)** repeats the single-fix-solves-everything error you've now correctly rejected in every mixed review across this entire session (Domain 1's logistics scenario, Domain 2's Domain-2 mixed review, Domain 3's healthtech scenario). A model upgrade does nothing for a mismeasured metric, a stale eval set's missing coverage, an already-unattributable bundled test result, or accumulated prompt bloat — and specifically for the hallucination issue, upgrading the model doesn't inherently fix a groundedness gap unless the actual fix (tying claims to verified file contents) is separately implemented.
- **C)** arbitrarily elevates one genuinely serious problem (correctly identified as having real compliance exposure) while dismissing four other independently real, evidenced problems as "minor," with no basis for that ranking beyond the hallucination issue's more visible legal stakes — the same unjustified-prioritization mistake rejected in your healthtech and legal-agent mixed reviews.
- **D)** treats all five problems as unfixable without a full rebuild, which both overstates the required remediation (every one of these five has a targeted, contained fix — a new metric, a refreshed eval set, a follow-up isolated test, a groundedness check, a token audit — none require rebuilding the system from scratch) and incorrectly implies these are pre-launch design flaws rather than what they actually are: five different manifestations of the same lesson repeated throughout Domain 4 — that evaluation and optimization are ongoing disciplines, and a system that launched well can still accumulate exactly these kinds of gaps over time if nothing is periodically re-verified.

**The meta-lesson closing out Domain 4**: every one of these five problems shares the same root structural cause — something was correct or reasonable *at one point in time* (a launch-time metric, an eval set, a test design, a working denial-letter process, a lean prompt) and nobody built in a mechanism to periodically re-check whether it still held. That's the single throughline across this entire domain, and it's the same instinct that should now be automatic: any evaluation artifact, metric, or optimization decision needs an answer to "how would we know if this stopped being true," not just "was this true when we set it up."
