**Scenario**

A financial advisory company wants to improve their Claude-powered portfolio-question chatbot. An engineer proposes a variant that bundles three changes at once: (1) switching from the current model to a newer model tier, (2) rewriting the system prompt with more detailed formatting instructions, and (3) adding two few-shot examples for complex tax-related questions. They run a properly powered, statistically sound A/B test comparing this bundled variant against the current control, tracking a full, appropriate metric set (accuracy, user satisfaction, latency, cost). The variant wins clearly and significantly on accuracy and satisfaction, with an acceptable latency and cost increase. The team ships the variant to 100% of traffic.

Two months later, the team wants to further optimize costs and proposes reverting just the model upgrade (component 1) to save money, reasoning "the model upgrade was probably only a small part of the accuracy gain, and the prompt and few-shot changes were likely doing most of the work — reverting just the model should preserve most of the benefit at lower cost." They have no way to actually verify this, since the original test only ever compared "all three changes together" against "none of the changes."

**Question**: What's the core methodological gap that's now limiting the team's ability to make this cost-optimization decision confidently, and what should they have done differently in the original test?

A) There's no gap — since the bundled variant won clearly on the metrics that matter, the original test was methodologically sound, and the team's current uncertainty about reverting just the model is an unrelated, separate question that doesn't reflect on the original test's design.

B) The core gap is that bundling three distinct changes into a single variant made it impossible to attribute the observed improvement to any one specific change — the team now has no data on how much each individual change (model upgrade, prompt rewrite, few-shot examples) contributed on its own, only on their combined effect. This is the same "can't isolate which change caused the result" problem as testing two simultaneous changes together without individual attribution. The team should have tested the changes individually (or in a structured multi-variant/factorial test isolating each component's contribution) from the start, which would let them now make an evidence-based decision about reverting just the model upgrade instead of guessing.

C) The issue is that the test should have used a smaller sample size, since large sample sizes make it harder to distinguish which specific change caused an effect.

D) The issue is irrelevant in retrospect; the team should simply run a brand new A/B test now, testing "current bundled variant" against "bundled variant minus the model upgrade," which fully resolves the problem with no loss of information compared to having tested components individually from the start.

**Why B is right**

Everything about this test's *execution* was sound — proper power, statistical significance, a full and appropriate metric set. The flaw isn't in how rigorously the test was run; it's in what question the test was actually designed to answer. "Bundled variant (all three changes) vs. control (none of the changes)" only ever tells you the *combined* effect of all three changes together — it structurally cannot tell you how much each one contributed individually, because no version of the test ever isolated them. This is precisely your PII-redaction scenario's lesson, generalized into a formal testing principle: "shipping two changes at once, untested against accuracy, means even now they can't cleanly attribute the failure to one lever versus the other" — same structure here, just with a *positive* outcome (an accuracy win) instead of a regression, which is exactly why it's easy to miss the same mistake was made. A win feels like validation and discourages the "wait, which part of this actually worked?" scrutiny that a regression naturally invites.

The cost is now concrete and immediate: the team wants to make a real business decision (drop the more expensive model tier to save cost) and has *no data* to base it on — only a plausible-sounding guess ("probably the prompt and few-shot changes did most of the work"). That guess could easily be wrong in either direction: maybe the model upgrade was actually the dominant driver and the prompt/few-shot changes contributed little, in which case reverting the model would erase most of the gain they fought to win. Or maybe the engineer's intuition is right and the model contributed almost nothing, in which case they've been needlessly paying premium-model cost for two months for a gain that came almost entirely from the free prompt changes. Without isolated data, they genuinely cannot distinguish between these very different real-world outcomes.

The fix, correctly named in B: test components individually (or via a structured multi-variant/factorial design — e.g., testing each change alone against control, or systematically testing combinations) from the start, so that the answer to "how much did each piece contribute" is something you *know*, not something you guess two months later when a cost-optimization question makes the gap in your knowledge suddenly expensive.

**Why the others are wrong**

- **A)** treats a clear win on the tracked metrics as proof the test design itself had no gaps — but "the test correctly detected that *something* about the bundle worked" and "the test can tell you which specific thing worked" are different capabilities, and only the first one was actually delivered here. The team's current inability to make an informed reversion decision is a *direct consequence* of the original test's design, not an unrelated new problem that appeared out of nowhere.
- **C)** inverts the actual relationship between sample size and attribution — smaller samples don't somehow make it *easier* to isolate which change caused an effect; if anything, isolating individual component effects (especially smaller ones) typically requires *more* data per arm, not less, since you're trying to detect potentially smaller individual effects rather than one larger combined one. This confuses statistical power (needs adequate size regardless) with experimental design (needs isolated arms), which are separate concerns.
- **D)** proposes a reasonable-sounding next step (test the bundle minus the model) but overstates it as fully solving the problem "with no loss of information compared to testing individually from the start" — that's not quite right. A new test comparing "bundle" vs. "bundle minus model" tells you the model's *marginal* contribution *given the other two changes already in place*, which is useful, but it's not the same as having known each of the three components' effects from the beginning — for instance, it still doesn't tell you whether the prompt rewrite and few-shot examples interact with each other, or what either would do in isolation without the other two, which a true factorial design from the outset would have revealed. It's a legitimate corrective step now, but claiming zero information loss compared to doing it right the first time overstates what a single follow-up comparison can recover.

**Pattern to remember, closing this out cleanly**: the PII-redaction lesson and this one are the same principle at two different scales — bundling multiple simultaneous changes destroys your ability to attribute outcomes to specific causes, whether the bundle produces a regression you're scrambling to diagnose or a win you later want to selectively unwind. The fix is always the same discipline: isolate one variable at a time (or use a structured design that lets you decompose combined effects), so that whatever the outcome, you actually know *why* it happened, not just *that* it happened.
