**Scenario**

A legal-tech company's contract-review assistant passed a thorough pre-launch evaluation process: a well-designed eval set with dedicated coverage of edge cases, a properly randomized and adequately-powered A/B test confirming it outperformed the previous version on accuracy, latency, and cost, and a clean diagnostic pass showing no prompt-failure or hallucination issues on the test set. It launched with strong confidence 9 months ago.

Since launch, the only thing tracked in production is a basic uptime/latency dashboard, reviewed occasionally by engineering — no ongoing accuracy sampling, no tracking of how often lawyers using the tool override or correct the assistant's flagged clauses, and no mechanism connecting production behavior back to the original eval set's categories at all. Nine months in, a client audit discovers the assistant has been systematically under-flagging a specific type of indemnification clause that became more common in contracts across the industry only in the last 5 months — a clause variant that didn't exist in the original eval set (built a year ago) and has never been checked against since, because nothing in production monitoring was designed to detect a shift in real-world accuracy at all, only infrastructure health.

**Question**: What's the core issue connecting the original evaluation process to what happened in production, and what should the team have done differently?

B) The core issue is that production monitoring was disconnected from the evaluation framework that validated the system pre-launch — uptime/latency monitoring tells you the system is running, but nothing was in place to continue checking the actual accuracy dimension the original eval set measured, against real, evolving production data, over time. The team should have built ongoing accuracy sampling (tying back to the eval categories), tracked override/correction rates from actual users (a free, available quality signal, as in your earlier feedback-loop material), and specifically monitored for emerging content patterns not represented in the original eval set — treating production monitoring as evaluation's continuation, not a separate, infrastructure-only concern.

Correct — and this scenario is specifically built to test the connective tissue between pre-launch evaluation and production monitoring, which is exactly the piece that was missing from your earlier coverage of this domain.

**Why B is right**

Notice what the pre-launch process actually validated versus what it *couldn't* validate, by definition: a rigorous eval set, a clean A/B test, and a solid diagnostic pass all confirmed the system performed well *against the world as it existed at the time of testing*. That's a real, valid, well-earned result — nothing about the original evaluation was poorly executed. But every one of those validations is inherently a snapshot, and the system's launch didn't freeze the world in place — new indemnification clause variants emerged industry-wide over the following months, in content the eval set had no way to represent because it didn't exist yet.

This is where the actual failure lives: **the evaluation discipline that produced real confidence at launch was never extended into production.** What got monitored afterward — uptime and latency — answers "is the system running," not "is the system still accurate on what it's actually seeing now." Those are different questions, and the gap between them is precisely where a real, client-discovered accuracy regression sat undetected for months. This is the direct, concrete illustration of the framing from the deep dive: "production monitoring *is* evaluation, just running indefinitely on real traffic instead of a fixed test set" — and here, that continuation simply never happened. The evaluation loop, functionally, stopped at launch.

The fix directly follows: **ongoing accuracy sampling** (not a one-time eval, a continuing one — tied back to the same categories/dimensions the original eval set measured, so you're tracking the same thing over time, not just at one instant), **override/correction rate tracking** (lawyers correcting the assistant's flagged clauses is exactly the kind of free, already-available quality signal from your feedback-loop material — the same "a human is already reviewing every output, don't throw that signal away" lesson from your loan-recommendation scenario, applied here to legal review), and **specific monitoring for emerging content patterns not represented in the original eval set** — a proactive extension of the eval-staleness lesson, watching for exactly the kind of drift (new clause types, new document formats, new terminology) that a frozen eval set can never catch on its own.

**Why the others are wrong**

- **A)** demands the impossible and misdiagnoses the actual gap — no evaluation process, however well-designed, can include test cases for content that didn't exist yet at the time of testing; that's not a flaw in the original process, it's an inherent limitation of any point-in-time evaluation. The real failure isn't that the eval set didn't anticipate the future — it's that nothing was built to notice *when* the future arrived and diverged from what was tested.
- **C)** correctly recognizes the eval-staleness component but incorrectly declares monitoring "irrelevant" to the diagnosis — this misses the entire point of why this scenario exists as a Domain 4 sub-topic distinct from what you already covered. Eval-set staleness explains why the *original* test set couldn't have caught this; the separate, additional failure is that *production monitoring* also never caught it once it started happening in the real world, over 9 months, because nothing was designed to. Both things are true and both matter — dismissing monitoring as irrelevant discards half of the actual lesson.
- **D)** overgeneralizes one instance of inadequate monitoring into a blanket claim that monitoring investment is categorically powerless against post-launch drift — but the fix B describes (ongoing accuracy sampling, override tracking, emerging-pattern monitoring) is precisely the kind of investment that *would* have caught this, likely well before a client audit had to surface it externally. Treating this as "an unavoidable cost of deploying any AI system" is a resignation that ignores the very real, evidence-based fixes available — the same complacency trap as declaring a fixable problem unsolvable in earlier scenarios across this session.

**Pattern to remember, closing this genuinely final gap in Domain 4**: pre-launch evaluation and production monitoring aren't two separate disciplines that happen to both matter — production monitoring is what pre-launch evaluation becomes once a system is live, and it needs to keep measuring the *same dimensions* (accuracy, not just infrastructure health) that the original evaluation validated, specifically because the world the system operates in keeps changing after launch even when nothing about the system itself does. A monitoring setup that only tracks "is it running" while the evaluation that justified shipping it tracked "is it accurate" has a structural blind spot baked in from day one — regardless of how good the original evaluation was.
