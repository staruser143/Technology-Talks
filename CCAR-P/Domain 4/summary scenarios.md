## A/B Testing — Quick Reference Summary

| # | Failure Mode | What Went Wrong | The Fix |
|---|---|---|---|
| **1** | **Insufficient sample size / premature stopping** | Concluded a "35% improvement" from ~180 visitors/arm (only ~3 purchases' difference) after just 6 hours — result likely noise, not signal | Predetermine required sample size/duration *before* starting the test; let it run to that threshold regardless of how early results look |
| **2** | **Incomplete metric set (proxy-metric blind spot)** | A statistically sound, well-powered test showed a real 8% watch-time lift — but only watch-time was tracked; the gain came from recommending longer content that hurt retention, undetected until 2 weeks post-rollout | Track the *full* metric set in the test itself (accuracy, cost, latency, safety, and downstream signals like retention) — not just the one metric the change targets |
| **3** | **Bundled changes destroy attribution** | Tested "model upgrade + prompt rewrite + few-shot examples" all at once vs. control; won clearly, but 2 months later couldn't tell which component to keep when trying to cut costs | Test components individually or via factorial design from the start, so each change's contribution is known, not guessed |
| **4** | **Non-random assignment (confounding)** | Assigned control/variant by signup date instead of randomly; variant group happened to also get discount promos + better sales qualification — impossible to attribute the completion-rate lift to the chatbot itself | Use true random assignment, independent of time or any other correlated factor, so both arms are comparable on everything except the change being tested |
| **5** | **Treating a result as a permanent gate** | Version B won 8 months ago and was never revisited; meanwhile international traffic share and a new loyalty feature transformed the user base — no one checked if B is still best | Re-test/re-evaluate periodically, especially after major shifts in traffic composition or product features — a valid past result isn't a permanent guarantee |
| **6** | **Using A/B testing when it's not the right tool at all** | Proposed a standard 50/50 live test on a clinical guardrail change (ambiguous dosage handling) — real patient records exposed to an unvalidated change for weeks, plus low volume made significance impractically slow | For high-stakes/hard-to-reverse or low-volume cases: offline eval against a held-out set first, human-in-the-loop validation, and staged/canary rollout instead of a full live split |

**The throughline across all six**: a test can look completely legitimate on the surface — significant, well-powered, cleanly executed — while still leading to a wrong or dangerous conclusion, because the flaw lives in the *design* (what's measured, how groups are assigned, whether changes are isolated, whether the method fits the stakes) rather than in whether the math was computed correctly. Always ask not just "was this test run well" but "was this the right test, measuring the right things, for this specific change."
