**Scenario**

A cybersecurity company built a Claude-powered system 18 months ago that classifies incoming network traffic descriptions as "known malicious pattern," "known benign pattern," or "requires human review." At launch, they built a 2,000-example eval set with ground-truth labels based on the threat-pattern database as it existed at that time, and the system scored 91% accuracy against it — strong, and it's remained the team's standard eval set ever since, re-run after every model or prompt update to confirm nothing regressed.

Eighteen months later, the system still scores 90-91% on this same eval set — consistently strong, no red flags from the team's regular testing. However, a recent external security audit found the system has been misclassifying several *newer* attack patterns that emerged in the last year as "requires human review" when they should be confidently flagged as "known malicious" — patterns that didn't exist when the eval set was built, and which the eval set's now-18-month-old ground truth labels have no representation of at all, since every example in the set reflects the threat landscape as it stood at launch.

**Question**: What's the core issue with how this eval set has been maintained, and what should the team do?

A) There's no issue — the consistent 90-91% score across 18 months of updates is strong evidence of stable, reliable performance, and the external audit's findings are likely unrelated to the eval set itself.

B) The core issue is eval-set staleness: the ground truth was accurate and representative when built, but the underlying reality it represents (the threat landscape) has continued evolving while the eval set stayed frozen at its original snapshot — meaning the eval set has been silently and increasingly failing to test the system against current, relevant cases, even though it still runs and reports a score every time. A consistently strong score on a stale eval set doesn't indicate current-world performance; it only indicates consistent performance against an increasingly outdated slice of reality. The team should periodically refresh the eval set with current examples (including recently emerged attack patterns), not just re-run the original fixed set indefinitely.

C) The issue is that the eval set should have been built without any temporal component at all, since any point-in-time snapshot will eventually become inaccurate; the team should have used a fundamentally different evaluation approach from the start.

D) The issue is unrelated to the eval set; this is purely a model capability gap, and the team should upgrade to a more capable model to handle novel attack patterns better.

Correct — and this scenario is the temporal counterpart to your superseded-policy RAG scenario from Domain 3, now applied one layer up: there, a *system* confidently served an outdated document as if it were current; here, an *evaluation harness* has been confidently reporting a good score against outdated ground truth for a year and a half, masking a real capability gap the whole time.

**Why B is right**

The mechanism is precise and worth tracing exactly: the eval set was genuinely good *when built* — accurate, representative ground truth reflecting the real threat landscape as it stood 18 months ago. Nothing about its original construction was flawed. The problem is that it was **never revisited**, while the thing it was measuring against — the threat landscape — kept moving. Every re-run since then has been testing the system against a progressively more outdated slice of reality, and because the eval set itself never changed, it structurally *cannot* detect a failure mode that only shows up on cases that didn't exist when the set was built. The system could be performing perfectly on every pattern the eval set knows about while simultaneously failing badly on every pattern that's emerged since — and the eval set's score would report the same reassuring 90-91% either way, because it's blind to the entire category of case where the real problem lives.

This is exactly why "consistent 90-91% across 18 months" isn't the reassurance the team took it to be — consistency against a frozen reference tells you the system hasn't regressed *on old cases*, but says nothing whatsoever about performance on new ones, which is precisely where the external audit found the actual failure (novel attack patterns misclassified as "requires review" instead of confidently flagged malicious). The fix, correctly stated in B, isn't to abandon the eval set or the general approach — it's to treat it as something requiring **periodic refresh**, incorporating current examples (including newly emerged attack patterns) alongside the still-valid historical ones, so the eval set's coverage evolves along with the reality it's meant to represent, rather than staying frozen at a single point in time indefinitely.

**Why the others are wrong**

- **A)** repeats the exact complacency this whole arc keeps testing — treating a consistent, unchanging score as inherently reassuring without asking what that score can and can't actually detect. A stable number from a stale test is not evidence of stable real-world performance; it's evidence that the test hasn't been checking the thing that changed. And the scenario explicitly connects the audit findings to eval-set staleness (the newer patterns "didn't exist when the eval set was built... which the eval set's ground truth has no representation of at all") — this isn't unrelated, it's the direct cause.
- **C)** overcorrects into rejecting the entire methodology rather than the specific maintenance failure — a point-in-time eval set isn't inherently flawed; every eval set is necessarily built at some point in time. The actual failure was never refreshing it afterward, not the fact that it originated from a snapshot. "Eventually becomes inaccurate" is true of any eval set for a domain that changes over time, and the fix for that is ongoing maintenance (periodic refresh), not a categorically different, never-fully-specified approach.
- **D)** reaches for a model-capability explanation without first establishing that the *evaluation process itself* was even capable of detecting the actual gap — this is the same premature-model-fix pattern rejected in essentially every scenario across this whole domain. It's entirely possible the model would perform reasonably well on novel patterns if it had ever been properly tested and iterated against them; jumping to "upgrade the model" skips past the more immediate, cheaper, and directly-evidenced fix (refresh the eval set so the team can actually see and address the real gap) in favor of an expensive change aimed at a problem that hasn't been correctly diagnosed yet.

All three produce the same outward symptom — a confident, trusted score — while the actual thing being measured against has a hidden flaw.
