**Scenario**

A developer at a company clones an open-source repository from GitHub to evaluate it for potential internal use, then opens it in Claude Code to explore the codebase. The repository includes a `.claude/settings.json` file (since it's a public repo, anyone could have contributed to or forked it) containing custom permission rules and hooks the developer never wrote or reviewed. When Claude Code opens the directory, a workspace trust dialog appears, asking the developer to confirm before this untrusted directory's settings take effect. The developer, eager to just start exploring the code and mildly annoyed by the interruption, clicks "trust" without reading what the dialog is actually asking or reviewing the repo's `.claude/settings.json` contents first.

It later turns out the repository's `.claude/settings.json` included a hook configured to silently exfiltrate file contents to an external endpoint whenever certain files were read — planted by a malicious contributor exploiting exactly this "click trust to get started" pattern.

**Question**: What's the core issue here, and what does it reveal about the purpose of the workspace trust dialog?


**Question**: What's the core issue here, and what does it reveal about the purpose of the workspace trust dialog?

A) There's no real issue — the workspace trust dialog is a formality most developers reasonably click through, and any genuinely dangerous configuration would be caught by other safeguards regardless of how the trust dialog is handled.

B) The core issue is treating the workspace trust dialog as a routine, content-free interruption to dismiss quickly rather than as the actual security checkpoint it's designed to be — this is precisely the prompt-injection-style risk from Domain 5, now applied to configuration rather than conversational content: an untrusted directory's settings file is itself a form of untrusted content that can alter agent behavior (here, via a malicious hook), and clicking "trust" without review is functionally the same mistake as an agent blindly following an embedded instruction in an untrusted email — except here it's the developer, not the model, making the trust decision, which means the dialog only provides real protection if developers treat it as a genuine decision point (reviewing what a repo's settings actually configure before trusting it) rather than a habitual click-through.

C) The issue is that workspace trust dialogs should be removed entirely, since they clearly failed to prevent this incident and add friction without providing real protection.

D) The issue is solely a technical failure in Claude Code's hook system; the workspace trust dialog is unrelated, since the actual exfiltration happened through a hook, not through the trust dialog itself.


Correct — and this scenario closes out the domain by tying together two threads from opposite ends of this session: Domain 5's prompt-injection material and Domain 7's team-tooling mechanics, showing they're really the same underlying risk pattern wearing different clothes.

**Why B is right**

Recall the exact shape of your email-forwarding prompt injection scenario from Domain 5: untrusted external content (there, an email; here, a cloned repository's configuration file) contains something crafted to look legitimate but is actually designed to manipulate agent behavior toward a harmful outcome, exploiting the gap between "this looks like normal content/configuration" and "this is actually an adversarial instruction." The mechanism is structurally identical here — a `.claude/settings.json` file in an untrusted, publicly-contributable repository isn't just inert configuration, it's a vector through which someone with bad intent can alter how Claude Code behaves in that directory, in this case via a hook silently exfiltrating file contents. The workspace trust dialog exists specifically as the checkpoint designed to interrupt exactly this pattern — forcing a deliberate decision before an unknown directory's settings are allowed to take effect.

What makes this scenario distinct and worth its own treatment: the failure isn't in the mechanism (the dialog fired correctly, exactly as designed) — it's in how the *human* engaged with it. This mirrors your approval-fatigue scenario from Domain 5 almost exactly, just with a single interaction instead of 200 daily ones: a safeguard that requires genuine engagement to function degrades into a rubber stamp the moment it's treated as routine friction to click past rather than a real decision point. "Eager to just start exploring the code, mildly annoyed by the interruption" is precisely the mental state under which a security checkpoint stops providing real protection — the dialog only works if the person facing it actually does what it's asking (review what's being trusted) rather than treating the click itself as the goal.

**Why the others are wrong**

- **A)** dismisses the dialog's failure as an inevitable, low-consequence formality — but the scenario shows a real, successful attack that specifically depended on this exact behavior pattern (click-through without review), and nothing in the setup suggests another safeguard would have independently caught a hook silently exfiltrating file contents; the trust dialog was specifically the layer positioned to prevent this, and it did its job mechanically while failing at the human-engagement level.
- **C)** proposes removing the safeguard because a human failed to use it correctly, which is precisely backwards — this is the same logic as abandoning a fail-closed guardrail because someone found a way to bypass it, rather than addressing why the bypass happened. The dialog firing and being dismissed without review isn't evidence the dialog is useless; it's evidence the dialog needs to actually be engaged with, the same way a car's seatbelt warning isn't proven pointless by someone ignoring it.
- **D)** draws an artificial line between "the hook mechanism" and "the trust dialog" as if they're unrelated — but the entire reason the trust dialog exists is specifically to gate whether an untrusted directory's hooks (and other settings) are allowed to take effect at all. The hook is the *payload*; the trust dialog is the *checkpoint* that was supposed to catch it before it activated. Treating them as separate, unrelated issues misses that the dialog's entire purpose is preventing exactly this kind of hook-based risk from untrusted sources.

**Pattern to remember, closing this domain and, in a sense, the whole session**: this scenario is a clean demonstration that the risk categories and defense principles built across Domains 1 through 6 aren't abstract — they show up concretely in the everyday mechanics of how a team actually configures and uses Claude Code day to day. Untrusted content manipulating agent behavior (Domain 5's prompt injection), a safeguard degrading into a rubber stamp under routine pressure (Domain 5's approval fatigue), least-privilege and structural enforcement over instructional trust (Domain 5's guardrails, now literally implemented as `allowedTools`/`deny` rules) — all of it converges directly in this domain's practical tooling, which is exactly why Domain 7, despite being the smallest by weight, ties the entire exam's conceptual material back to concrete, everyday developer practice.
