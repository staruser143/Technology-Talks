**Scenario**

A company's Claude-powered customer-onboarding system was documented thoroughly at launch two years ago — architecture diagrams, model choice rationale, guardrail explanations, all clear and well-written at the time. Since then, the system has evolved substantially through several rounds of iteration: the original single-model workflow was restructured into a multi-agent system with three specialized subagents, the model tier was upgraded twice, and two of the original guardrails were replaced with different mechanisms after being found insufficient. None of these changes were reflected back into the original documentation, which still describes the launch-era single-model workflow architecture.

A new compliance auditor, preparing for a regulatory review, pulls the existing documentation to understand how the system makes decisions and what safeguards are in place — and, working entirely from what's documented, produces a compliance report describing guardrails and an architecture that no longer actually exist in the running system, missing the actual current safeguards (and their own possible gaps) entirely.

**Question**: What's the core documentation issue here, and what should the team do?


**Question**: What's the core documentation issue here, and what should the team do?

A) There's no issue with the documentation itself — it was accurate and well-written when created, and the compliance auditor should have independently verified the actual running system rather than relying on documentation at all, so the failure is entirely the auditor's responsibility.

B) The core issue is **documentation staleness** — the same "accurate when created, silently outdated as the underlying system evolved" pattern seen with eval sets and A/B test conclusions elsewhere in this session, now applied to architectural documentation itself. Two years of substantial changes (multi-agent restructuring, model upgrades, guardrail replacements) were never reflected back into the documentation, meaning it confidently describes a system that no longer exists — and unlike a stale eval set quietly producing a misleading score, stale architecture documentation actively misdirects anyone who trusts it, here producing a compliance report describing safeguards that aren't real and missing the actual current ones. The team should treat documentation as something requiring ongoing maintenance tied to the system's actual change process — updated whenever architecture changes, not written once at launch and left static — and the auditor's report should be corrected based on the actual current system, not the documented one.

C) The issue is that documentation should never be written until a system is fully mature and no longer expected to change, since any documentation of an evolving system is inherently premature and likely to become inaccurate.

D) The issue is solely the compliance auditor's failure to ask engineering directly what the current architecture looks like; documentation is a secondary reference at best and bears no real responsibility for being kept current.


Correct — and this scenario is the documentation-specific instance of a pattern you've now diagnosed correctly across nearly every domain this session: something accurate at a point in time, treated as permanently valid, silently drifting out of sync with reality while everyone continues trusting it.

**Why B is right**

Trace the direct parallel, because it's worth seeing how consistently this exact shape recurs: your eval-staleness scenario showed a test set that was accurate when built silently failing to represent a changed threat landscape, producing a misleadingly reassuring score. Your travel-booking A/B test scenario showed a valid result treated as a permanent gate while the underlying user base shifted underneath it. This scenario is the same mechanism, now applied to documentation: accurate and well-written *at launch*, genuinely useful at the time, and then never revisited across two years of substantial, real architectural change — a full restructuring into a multi-agent system, two model upgrades, two guardrail replacements. None of that evolution made it back into the record.

What makes this instance particularly consequential, and worth distinguishing from the eval-staleness case: a stale eval set produces a *misleading number* someone might question if it looks too good. Stale documentation, by contrast, produces an *actively wrong description of reality* that someone can reasonably trust completely, precisely because documentation is supposed to be the authoritative record of "how does this system actually work." The compliance auditor did exactly what documentation exists to enable — reviewed the written record instead of needing to independently reverse-engineer the system from scratch — and was led directly into producing a report describing safeguards that don't exist, while missing the actual current mechanisms (and any real gaps in them) entirely. This isn't a case of documentation gradually losing precision at the margins; it's a case where the documented architecture and the running architecture have diverged completely.

The fix, correctly stated in B: documentation needs a maintenance discipline tied to the system's actual change process, not a one-time artifact from launch. Whenever a real architectural change happens — a restructuring, a model swap, a guardrail replacement — updating the documentation should be part of that change, the same way you'd expect a code change to come with its own tests. And practically, right now, the compliance report itself needs to be redone against the actual current system, not the documented one, since the documented one no longer describes anything real.

**Why the others are wrong**

- **A)** shifts the entire failure onto the auditor for trusting documentation, but this misunderstands what documentation is *for* — if documentation can't be relied upon without independent verification of the entire system from scratch every time, it provides essentially no value at all, and the entire premise of Domain 6's documentation objective ("provide implementation guidance" that others can actually use) collapses. The auditor behaved reasonably; the documentation failed to be what it claimed to be.
- **C)** overcorrects into avoiding documentation altogether until a system is "mature and no longer expected to change" — but this describes a state most real production systems never actually reach, since ongoing iteration is normal and expected (directly your Domain 4 lesson: evaluation and optimization are continuous, not one-time). Waiting indefinitely for permanence before documenting anything would mean most systems never get documented at all, which is a much worse outcome than documentation that requires periodic updates.
- **D)** repeats A's mistake in a different form — placing the entire burden on the auditor to bypass documentation and go straight to engineering, which again treats documentation as functionally worthless rather than recognizing that its value depends specifically on being kept current. If documentation "bears no real responsibility for being kept current," it's unclear what purpose it serves at all beyond a historical snapshot of how the system looked on day one.

**Pattern to remember, closing the documentation arc**: this is the same "accurate once, never re-verified, silently diverges from reality" failure mode you've now seen applied to eval sets, ground truth, A/B test conclusions, and cost/token budgets across this entire session — documentation is simply the latest artifact type where the lesson applies. Anything that describes a system's current state needs an answer to "how would we know if this stopped being true," and for architecture documentation specifically, that answer needs to be "it gets updated as part of the same process that changes the system," not "someone remembers to go back and fix it eventually."
