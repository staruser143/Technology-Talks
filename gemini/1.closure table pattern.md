The Closure Table pattern is a database design pattern used to store and manage hierarchical data (such as organizational charts, category trees, or folder structures) in a relational database.
Unlike traditional adjacency list models (where each node just stores a reference to its immediate parent), a closure table explicitly stores every parent-child relationship path in a separate mapping table, regardless of how many levels apart the nodes are.
How It Works
A closure table relies on two main tables:
 * Nodes Table: Stores the actual entity data.
 * Closure Table: Stores every hierarchical path, including self-references (a node pointing to itself) and all ancestor-descendant combinations.
Example Schema
1. Categories Table (Nodes)
| category_id | name |
|---|---|
| 1 | Electronics |
| 2 | Computers |
| 3 | Laptops |
| 4 | Smartphones |
2. CategoryTree Table (Closure Table)
| ancestor | descendant | depth |
|---|---|---|
| 1 | 1 | 0 |
| 1 | 2 | 1 |
| 1 | 3 | 2 |
| 1 | 4 | 1 |
| 2 | 2 | 0 |
| 2 | 3 | 1 |
| 3 | 3 | 0 |
| 4 | 4 | 0 |
Note: The depth column tracks how many levels separate the ancestor and descendant (e.g., Electronics to Laptops has a depth of 2).
Common Operations
 * Find all descendants of a node (e.g., all subcategories under Electronics):
   SELECT c.* 
FROM Categories c
JOIN CategoryTree t ON c.category_id = t.descendant
WHERE t.ancestor = 1;

 * Find all ancestors/path up to a node (e.g., the path to Laptops):
   SELECT c.* 
FROM Categories c
JOIN CategoryTree t ON c.category_id = t.ancestor
WHERE t.descendant = 3
ORDER BY t.depth DESC;

 * Insert a new node:
   Insert a self-reference row into the closure table (depth = 0), plus rows for every ancestor of the new parent.
 * Delete a subtree:
   Delete any rows in the closure table where the descendant is part of the subtree you want to remove.
Pros and Cons
Advantages
 * High Performance for Reads: Finding all ancestors or descendants is a simple, fast JOIN operation without needing recursive Common Table Expressions (CTEs).
 * Flexibility: Easily handles deep hierarchies and complex trees.
 * Standard SQL Compatibility: Works efficiently across almost all relational database management systems.
Disadvantages
 * Storage Overhead: Requires significantly more storage space because it saves every path permutation (an O(N^2) growth pattern for deep trees, though manageable for typical use cases).
 * Complex Writes: Inserting, moving, or deleting nodes requires careful management of multiple rows in the closure table to keep the paths accurate.
