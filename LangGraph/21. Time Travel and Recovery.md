# Time Travel and Crash Recovery in LangGraph 
- Built on the checkpointing and persistence system. Every time a node runs, the checkpointer takes an immutable snapshot of the graph's state and stores it under a given session key **(thread_id) with a unique checkpoint_id**.

## 1. Crash Recovery
- **Allows a workflow that fails midway** — due to an API timeout, network failure, or process termination—to resume from the last successful checkpoint instead of restarting from scratch.
 * **How It Works**: Every node execution saves its update to the persistent checkpointer (such as SqliteSaver or PostgresSaver) before the graph proceeds to the next node. If an unhandled exception halts the system, intermediate progress remains committed to disk or database.
 * **Resuming**: Calling graph.invoke(None, config) using the same thread_id prompts LangGraph to inspect the last valid checkpoint for that thread and resume execution directly from whichever node was scheduled next (snapshot.next).

# Reconnecting to an existing thread after an interruption or failure:
```python
config = {"configurable": {"thread_id": "session-101"}}
```

# Passing `None` instructs LangGraph to resume from the latest saved snapshot
```python
resumed_result = graph.invoke(None, config)
```

## 2. Time Travel (Replaying, Inspecting & Forking)
Time travel is the ability to **inspect historical snapshots, roll back to an earlier point in execution, modify the state, and fork execution down an alternate path**.

### A. Browsing State History
Using graph.get_state_history(config), you can iterate backward through every step the agent executed:
```python
config = {"configurable": {"thread_id": "session-101"}}
```
# Get all checkpoints in reverse chronological order
```python
history = list(graph.get_state_history(config))

for snapshot in history:
    print(f"Checkpoint ID : {snapshot.config['configurable']['checkpoint_id']}")
    print(f"Step Index    : {snapshot.metadata.get('step')}")
    print(f"Next Node     : {snapshot.next}")
    print(f"State Values  : {snapshot.values}\n")
```
### B. Replaying from a Specific Step
To re-run the graph starting from an earlier checkpoint, supply the historical checkpoint_id in the configuration:
target_checkpoint_id = "1ef82a74-..."  # ID from history
```python
replay_config = {
    "configurable": {
        "thread_id": "session-101",
        "checkpoint_id": target_checkpoint_id
    }
}

# Executes forward from that specific historical point
result = graph.invoke(None, replay_config)
```

### C. Forking / State Mutation ("What-If" Analysis)
We can alter state at a past point to test alternative trajectories. Updating the state at a historical checkpoint_id creates a branch without overwriting other historical records:
```python
# 1. Target a past snapshot
past_config = {
    "configurable": {
        "thread_id": "session-101",
        "checkpoint_id": "1ef82a74-..."
    }
}

# 2. Modify state at that historical checkpoint
new_config = graph.update_state(
    past_config,
    {"query": "Provide a concise summary instead"}
)

# 3. Resume from the modified checkpoint to fork into a new path
forked_result = graph.invoke(None, new_config)
```

## Comparison
| Feature | Crash Recovery | Time Travel |
|---|---|---|
| Primary Goal | Fault tolerance and continuity. | Debugging, human intervention, and hypothetical testing. |
| Target Checkpoint | The latest valid checkpoint in the thread. | Any historical checkpoint selected by ID. |
| State Mutation | Typically resumed as-is, or lightly patched via update_state(). | Frequently edited to explore alternate execution paths. |
| Checkpointer Requirement | Persistent storage (SqliteSaver, PostgresSaver) to survive process restarts. | Works in memory (MemorySaver) for interactive debugging or in persistent storage. |
