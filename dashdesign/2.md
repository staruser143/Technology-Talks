Here’s a concrete **PostgreSQL-style schema** with sample data to make the design tangible. I’ll use the **Party/Role** pattern and focus on the hierarchy + commission logic.

## 📦 Table Structures & Sample Data

### 1. `party` (base table)
```sql
CREATE TABLE party (
    id SERIAL PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    tax_id VARCHAR(20) UNIQUE,
    created_at TIMESTAMP DEFAULT NOW()
);
```

### 2. `broker` & `agency` (role tables)
```sql
CREATE TABLE broker (
    party_id INT PRIMARY KEY REFERENCES party(id),
    license_number VARCHAR(50) NOT NULL,
    license_expiry DATE NOT NULL,
    is_active BOOLEAN DEFAULT TRUE
);

CREATE TABLE agency (
    party_id INT PRIMARY KEY REFERENCES party(id),
    agency_code VARCHAR(20) UNIQUE NOT NULL,
    parent_agency_id INT REFERENCES agency(party_id) -- allows agency-to-agency hierarchy
);
```

### 3. `party_relationship` (hierarchy edges – flexible)
```sql
CREATE TABLE party_relationship (
    id SERIAL PRIMARY KEY,
    parent_party_id INT NOT NULL REFERENCES party(id),
    child_party_id INT NOT NULL REFERENCES party(id),
    relationship_type VARCHAR(50) NOT NULL, -- 'OWNS', 'SUPERVISES', 'MANAGES'
    valid_from DATE NOT NULL,
    valid_to DATE DEFAULT '9999-12-31',
    UNIQUE(parent_party_id, child_party_id, relationship_type)
);
```

**Sample data (shows both agency and broker reporting):**
| parent_party_id | child_party_id | relationship_type | valid_from | valid_to |
|----------------|----------------|-------------------|------------|----------|
| 1 (National) | 2 (Texas Regional) | OWNS | 2020-01-01 | 9999-12-31 |
| 2 (Texas Regional) | 3 (Dallas Office) | OWNS | 2021-06-01 | 9999-12-31 |
| 2 (Texas Regional) | 5 (Austin Office) | OWNS | 2022-03-15 | 9999-12-31 |
| 3 (Dallas Office) | 4 (Jane Smith) | SUPERVISES | 2023-01-15 | 9999-12-31 |

> This gives you a **tree**: National → Texas Regional → Dallas → Jane Smith.

### 4. `contract` (agreement with insurer)
```sql
CREATE TABLE contract (
    id SERIAL PRIMARY KEY,
    agency_party_id INT NOT NULL REFERENCES party(id),
    insurer_name VARCHAR(200),
    product_line VARCHAR(100), -- 'PPO', 'HMO', 'DENTAL'
    base_commission_rate DECIMAL(5,2), -- e.g., 8.50%
    effective_date DATE NOT NULL,
    termination_date DATE DEFAULT NULL
);
```

**Sample:**
| id | agency_party_id | insurer_name | product_line | base_rate | effective_date |
|----|----------------|--------------|--------------|-----------|----------------|
| 1 | 2 (Texas Regional) | BlueCross TX | PPO | 8.50 | 2024-01-01 |

### 5. `commission_split` (per policy)
```sql
CREATE TABLE commission_split (
    id SERIAL PRIMARY KEY,
    policy_number VARCHAR(50) NOT NULL,
    contract_id INT NOT NULL REFERENCES contract(id),
    recipient_party_id INT NOT NULL REFERENCES party(id),
    split_percentage DECIMAL(5,2) NOT NULL,
    CHECK (split_percentage >= 0 AND split_percentage <= 100)
);
```

**Sample for one policy sold by Jane (party 4) under Texas Regional’s contract:**
| policy_number | contract_id | recipient_party_id | split_percentage |
|---------------|-------------|---------------------|------------------|
| POL-2026-001 | 1 | 4 (Jane Smith) | 50.00 |
| POL-2026-001 | 1 | 3 (Dallas Office) | 30.00 |
| POL-2026-001 | 1 | 2 (Texas Regional) | 20.00 |

> **Total = 100%** – enforced by your application or a trigger.

## 🔍 Query Example: Full Hierarchy for Jane Smith
```sql
WITH RECURSIVE hierarchy AS (
    SELECT parent_party_id, child_party_id, relationship_type
    FROM party_relationship
    WHERE child_party_id = 4
    UNION ALL
    SELECT pr.parent_party_id, pr.child_party_id, pr.relationship_type
    FROM party_relationship pr
    JOIN hierarchy h ON pr.child_party_id = h.parent_party_id
)
SELECT p.id, p.name, h.relationship_type
FROM hierarchy h
JOIN party p ON h.parent_party_id = p.id;
```

**Result:** Shows Jane → Dallas (Supervises) → Texas Regional (Owns) → National (Owns).

## ✅ Why This Works

- **Flexible hierarchy** – handles multi-parent or matrix structures if needed later.
- **Time‑aware** – you can track reorganizations and commission changes historically.
- **Clear separation** – party data never duplicates, and roles/contracts are modular.
