## 🏗️ Schema Design (PostgreSQL with JSONB)

### 1. `party` – now with JSONB for flexible attributes
```sql
CREATE TABLE party (
    id SERIAL PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    tax_id VARCHAR(20) UNIQUE,
    party_type VARCHAR(20) NOT NULL, -- 'INDIVIDUAL', 'AGENCY'
    attributes JSONB DEFAULT '{}', -- flexible fields
    created_at TIMESTAMP DEFAULT NOW()
);

-- Index for JSONB queries (e.g., filtering by state license)
CREATE INDEX idx_party_attributes ON party USING GIN (attributes);
```

### 3. `hierarchy` – stores the tree with path caching (critical!)
```sql
CREATE TABLE hierarchy (
    id SERIAL PRIMARY KEY,
    parent_id INT REFERENCES party(id),
    child_id INT REFERENCES party(id),
    relationship_type VARCHAR(50),
    valid_from DATE NOT NULL,
    valid_to DATE DEFAULT '9999-12-31',
    
    -- Denormalized path for fast queries (like MongoDB's nested docs)
    path INT[] GENERATED ALWAYS AS (
        -- Populated via trigger/function – see below
    ) STORED,
    
    depth INT GENERATED ALWAYS AS (array_length(path, 1)) STORED
);

-- Index for path queries
CREATE INDEX idx_hierarchy_path ON hierarchy USING GIN (path);
```

### 5. `commission_split` – still relational (financial integrity!)
```sql
CREATE TABLE commission_split (
    id SERIAL PRIMARY KEY,
    policy_number VARCHAR(50) NOT NULL,
    contract_id INT REFERENCES contract(id),
    recipient_party_id INT REFERENCES party(id),
    split_percentage DECIMAL(5,2) NOT NULL,
    calculated_amount DECIMAL(12,2), -- denormalized for speed
    CHECK (split_percentage >= 0 AND split_percentage <= 100)
);

-- Ensure total = 100% per policy
CREATE UNIQUE INDEX idx_policy_total ON commission_split (policy_number) 
WHERE (SELECT SUM(split_percentage) FROM commission_split cs2 
       WHERE cs2.policy_number = commission_split.policy_number) != 100;
```

## 🔥 Powerful Queries (Best of Both Worlds)

### 1. Find all descendants of National (using path)
```sql
SELECT p.*, h.depth
FROM hierarchy h
JOIN party p ON p.id = h.child_id
WHERE h.path @> ARRAY[1] -- contains National's ID
  AND h.child_id != 1
ORDER BY h.depth;
```

### 2. Find brokers with CA license expiring soon (JSONB query)
```sql
SELECT p.name, b.license_data
FROM broker b
JOIN party p ON p.id = b.party_id
WHERE b.license_data @> '{"CA": {"expiry": "2026-09-15"}}'::jsonb
   OR b.license_data -> 'CA' ->> 'expiry' < '2027-01-01';
```

### 3. Agencies offering volume-based tiers (JSONB query)
```sql
SELECT p.name, c.commission_rules -> 'tiers' AS tiers
FROM contract c
JOIN party p ON p.id = c.agency_party_id
WHERE c.commission_rules ? 'tiers'
  AND c.commission_rules -> 'tiers' @> '[{"volume_min": 0}]';
```

### 4. Complex: Total commission for Jane's policy with dynamic rates
```sql
WITH policy_contract AS (
    SELECT 
        cs.policy_number,
        cs.recipient_party_id,
        cs.split_percentage,
        c.commission_rules,
        (c.commission_rules ->> 'base_rate')::DECIMAL AS base_rate
    FROM commission_split cs
    JOIN contract c ON c.id = cs.contract_id
    WHERE cs.policy_number = 'POL-2026-001'
)
SELECT 
    p.name,
    pc.split_percentage,
    pc.base_rate,
    (pc.split_percentage / 100) * pc.base_rate AS effective_rate,
    -- Dynamic calculation with JSONB tier logic (in app or plpgsql)
    (pc.split_percentage / 100) * pc.base_rate * 1000 AS commission_amount
FROM policy_contract pc
JOIN party p ON p.id = pc.recipient_party_id;
```

## 🚀 Automatic Path Maintenance (Trigger)

```sql
CREATE OR REPLACE FUNCTION update_hierarchy_path()
RETURNS TRIGGER AS $$
DECLARE
    parent_path INT[];
BEGIN
    -- Get parent's path
    SELECT path INTO parent_path 
    FROM hierarchy 
    WHERE child_id = NEW.parent_id 
      AND valid_to = '9999-12-31';
    
    -- Build new path
    NEW.path = parent_path || NEW.child_id;
    
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER set_hierarchy_path
BEFORE INSERT OR UPDATE ON hierarchy
FOR EACH ROW
EXECUTE FUNCTION update_hierarchy_path();
```

## 📊 When to Use JSONB vs. Relational Columns

| Use JSONB For | Use Relational Columns For |
|---------------|---------------------------|
| Dynamic attributes (languages, specialties) | Party ID, Name, Tax ID (reference data) |
| State-specific licensing (varies by broker) | License number (if uniform) |
| Commission tiers/overrides (complex, variable) | Base commission rate (if simple) |
| Product eligibility rules | Policy number, Dates, Foreign keys |
| Quick prototype/iterative changes | Financial integrity (splits, percentages) |

## ✅ Advantages of This Approach

| Benefit | How It Helps |
|---------|--------------|
| **Schema flexibility** | Add new broker attributes (e.g., `"digital_signature": true`) without `ALTER TABLE` |
| **Query power** | SQL joins for reporting + JSONB operators for flexible searches |
| **Data integrity** | Foreign keys, constraints, and ACID for commissions |
| **Performance** | GIN indexes on JSONB + B-tree indexes on relational columns |
| **Migration ease** | Gradually move attributes from JSONB to columns as they become standardized |
