Yes — **if you query raw transaction tables at request time for every dashboard widget, it can become slow**, especially when:

- Data volumes are large
- Many users open dashboards at the same time
- Queries involve many joins
- You use expensive operations like `COUNT(DISTINCT ...)`
- Dashboards require sub-second response times
- You are calculating complex insurance metrics like commissions, renewals, retention, and splits

But that does **not** mean you should avoid Redshift. It means you should design the dashboard layer correctly.

The usual pattern is:

```text
Raw detail in Redshift
        +
Pre-aggregated summary tables / materialized views
        +
BI cache / semantic layer
        =
Fast drill-down dashboards
```

---

# 1. Do not query raw fact tables directly for every dashboard render

If your dashboard shows:

- Applications today
- Renewals expiring in 30 days
- Commission earned this month
- Retention rate by region
- Applications by agency
- Applications by agent

and every widget runs a query like:

```sql
SELECT
    region,
    agency,
    subagency,
    agent,
    COUNT(application_id),
    SUM(estimated_premium)
FROM fact_applications
JOIN dim_agent ...
JOIN dim_agency ...
JOIN dim_region ...
JOIN dim_market_category ...
WHERE application_date >= CURRENT_DATE - 365
GROUP BY
    region,
    agency,
    subagency,
    agent;
```

then performance may degrade.

That query might be fine for an analyst running one report, but not ideal for a dashboard rendered for many users every morning.

# 2. Use pre-aggregated tables for dashboard rendering

For fast dashboards, create summary tables at the levels users most commonly query.

Example:

```sql
agg_daily_sales_metrics
-----------------------
metric_date
region_name
market_category_name
agency_name
subagency_name
agent_name
applications
bound_applications
application_premium
renewals
renewed_premium
expiring_premium
commission_amount
```

Then your dashboard queries become much simpler:

```sql
SELECT
    region_name,
    SUM(applications) AS applications,
    SUM(renewals) AS renewals,
    SUM(commission_amount) AS commission_amount
FROM agg_daily_sales_metrics
WHERE metric_date >= CURRENT_DATE - 30
GROUP BY region_name;
```

Drill to agency:

```sql
SELECT
    agency_name,
    SUM(applications) AS applications,
    SUM(renewals) AS renewals,
    SUM(commission_amount) AS commission_amount
FROM agg_daily_sales_metrics
WHERE metric_date >= CURRENT_DATE - 30
  AND region_name = 'West'
GROUP BY agency_name;
```

Drill to sub-agency:

```sql
SELECT
    subagency_name,
    SUM(applications) AS applications,
    SUM(renewals) AS renewals,
    SUM(commission_amount) AS commission_amount
FROM agg_daily_sales_metrics
WHERE metric_date >= CURRENT_DATE - 30
  AND region_name = 'West'
  AND agency_name = 'Agency 101'
GROUP BY subagency_name;
```

Drill to agent:

```sql
SELECT
    agent_name,
    SUM(applications) AS applications,
    SUM(renewals) AS renewals,
    SUM(commission_amount) AS commission_amount
FROM agg_daily_sales_metrics
WHERE metric_date >= CURRENT_DATE - 30
  AND region_name = 'West'
  AND agency_name = 'Agency 101'
  AND subagency_name = 'Sub-agency 205'
GROUP BY agent_name;
```

These queries are much faster because they scan already-aggregated rows.

# 3. Use materialized views for near-real-time summaries

Redshift materialized views can help you avoid repeated heavy computation.

Example:

```sql
CREATE MATERIALIZED VIEW mv_daily_broker_metrics
AUTO REFRESH
AS
SELECT
    f.application_date_key AS metric_date,
    h.region_name,
    h.agency_name,
    h.subagency_name,
    h.agent_name,
    m.market_category_name,
    COUNT(f.application_id) AS applications,
    SUM(f.estimated_premium) AS application_premium,
    SUM(CASE WHEN f.bound_indicator = 1 THEN 1 ELSE 0 END) AS bound_applications
FROM fact_applications f
JOIN dim_sales_hierarchy h
    ON f.sales_hierarchy_key = h.sales_hierarchy_key
JOIN dim_market_category m
    ON f.market_category_key = m.market_category_key
GROUP BY
    f.application_date_key,
    h.region_name,
    h.agency_name,
    h.subagency_name,
    h.agent_name,
    m.market_category_name;
```

Then dashboards query:

```sql
SELECT *
FROM mv_daily_broker_metrics;
```

The heavy aggregation is done in advance, not every time a user opens the dashboard.

# 4. Use a layered aggregation strategy

For insurance broker dashboards, I would recommend this pattern:

## Layer 1: Detail layer

This keeps full transaction-level detail.

Examples:

```text
fact_applications
fact_renewals
fact_commissions
fact_policy_transactions
```

This layer is used for:

- Auditing
- Deep drill-through
- Data reconciliation
- Custom analysis
- Commission disputes
- Export to finance systems

## Layer 2: Daily aggregate layer

This is the main dashboard layer.

Examples:

```text
agg_daily_agent_metrics
agg_daily_agency_metrics
agg_daily_region_metrics
agg_daily_market_metrics
```

This layer supports:

- KPI tiles
- Trend charts
- Drill-down by agency/sub-agency/agent
- Month-to-date and year-to-date summaries

## Layer 3: Real-time or near-real-time layer

This is optional but useful for intraday monitoring.

Examples:

```text
mv_today_application_metrics
mv_current_month_broker_metrics
mv_renewal_pipeline_daily
```

This layer can be refreshed every few minutes using:

- Redshift streaming ingestion
- Micro-batch ETL
- Materialized view auto refresh
- AWS Glue jobs
- Stored procedures

---

# 5. Real-time does not always mean query raw events instantly

For broker dashboards, “real-time” usually means:

```text
Data is fresh within seconds to a few minutes.
```

It usually does not mean:

```text
Every dashboard widget must calculate from raw events in milliseconds.
```

So instead of querying raw event streams directly, do this:

```text
Application event
    -> Kinesis / MSK
        -> Redshift streaming ingestion
            -> fact table
                -> materialized view / aggregate table
                    -> dashboard
```

The dashboard reads from the aggregate layer, while the aggregate layer is refreshed continuously or every few minutes.

```sql
  AND agency_name = 'Agency 101'

LIMIT 100;
```

# 7. Redshift result cache can also help

Redshift has a result cache that can return cached results for repeated queries.

This helps when many users open the same dashboard and run the same query.

For example, if 100 managers open the same dashboard at 8:00 AM and request:

```sql
SELECT
    region_name,
    SUM(applications)
FROM mv_daily_broker_metrics
WHERE metric_date = CURRENT_DATE
GROUP BY region_name;
```

Redshift may serve repeated requests from cache instead of recomputing every time.

However, you should not rely only on result cache. Pre-aggregation is still better.

# 9. Avoid expensive dashboard queries

Some query patterns are slow for dashboards.

## Expensive

```sql
COUNT(DISTINCT application_id)
COUNT(DISTINCT policy_id)
COUNT(DISTINCT client_id)
```

These can be expensive at large scale.

If you need distinct counts, consider:

- Precomputing them
- Using approximate distinct counts where acceptable
- Storing distinct counts in aggregate tables
- Designing fact tables so distinct counts become simple counts

## Expensive

```sql
Many-to-many joins
Bridge tables without careful design
Late-binding hierarchies at query time
```

For insurance hierarchies, precompute the effective hierarchy in the fact or bridge layer where possible.

## Expensive

```sql
Calculating complex commission splits on the fly
```

If commissions are split by agent, sub-agency, agency, carrier, and policy version, precompute the allocated commission fact table.

Example:

```sql
fact_commission_allocation
--------------------------
commission_id
policy_id
agent_key
agency_key
subagency_key
region_key
market_category_key
commission_amount
allocation_percentage
```

Then dashboards simply sum:

```sql
SUM(commission_amount)
```

# 12. When direct query is still okay

Direct request-time querying can still be fine if:

- Data volume is moderate
- Queries are well-tuned
- You use Redshift Serverless or properly sized clusters
- You use sort keys and distribution keys effectively
- You limit dashboards to small time windows
- You query from marts/views instead of raw tables
- Concurrency is not extremely high
- Dashboard users tolerate 2–5 second load times

For example, a manager checking one agency’s performance for the current month may be fine with direct query.

But for a large brokerage with hundreds or thousands of users, pre-aggregation is safer.

---

# 13. When direct query is not enough

Direct query may be too slow if:

- You have billions of transactions
- Dashboards have many widgets
- Many users open dashboards simultaneously
- You need sub-second response
- You use complex distinct counts
- You calculate commission allocations on the fly
- You join many slowly changing dimensions
- You query several years of data by default

In those cases, use:

```text
Aggregate tables
Materialized views
BI extracts/caches
Application-level cache
```

---

# 14. If you need sub-second operational screens

If the requirement is not just a dashboard but an operational screen embedded inside a broker portal, for example:

```text
Show this agent’s commission today in under 50 milliseconds
```

then Redshift may not be the best direct query engine.

For that kind of millisecond-level operational lookup, consider:

```text
Amazon DynamoDB
Amazon ElastiCache
Amazon OpenSearch
Aurora read replicas
```

But for analytical dashboards and near-real-time management reporting, Redshift is still a strong choice.

A common hybrid pattern is:

```text
Redshift for analytics and dashboards
DynamoDB/ElastiCache for operational low-latency screens
```

# 16. Simple rule

Use this rule:

```text
Dashboard rendering should usually query pre-aggregated data.
Drill-through to individual records can query detailed data.
Raw transactional tables should not be the first source for every dashboard render.
```

So the answer is:

> Yes, querying raw Redshift tables at request time can be slow if used directly for every dashboard widget.  
> But if you use proper dimensional modeling, aggregate tables, materialized views, Redshift tuning, and BI caching, Redshift can support fast drill-down and roll-up dashboards for insurance broker metrics.
