# 3. Redshift vs Pinot vs Druid: core difference

## Redshift

Redshift is a **data warehouse**.

It is best when you need:

```text
Historical analytics
BI dashboards
Complex SQL
Joins across dimensions
Commission reporting
Renewal analytics
Year-over-year comparisons
Governed metrics
Self-service reporting
```

Redshift can support near-real-time dashboards, but it is not primarily a millisecond-latency operational analytics engine.

Typical dashboard latency:

```text
Seconds to tens of seconds if unoptimized
Sub-second to a few seconds with aggregates, materialized views, caching
```

---

## Apache Pinot

Apache Pinot is a **real-time distributed OLAP datastore**.

It is optimized for:

```text
Low-latency queries
High concurrency
Dimensional filtering
Group-by aggregations
User-facing analytics
Streaming ingestion from Kafka
Pre-aggregated metrics
```

Typical dashboard latency:

```text
Milliseconds to low seconds
```

Pinot is often a good fit when dashboards are embedded in an application and used by many users simultaneously.

---

## Apache Druid

Apache Druid is also a **real-time OLAP datastore**, but it is especially strong for:

```text
Event-driven analytics
Time-series analytics
High ingest rates
Rollup at ingestion
Operational monitoring
Large-scale aggregation
```

Typical dashboard latency:

```text
Milliseconds to low seconds
```

Druid is commonly used for telemetry, network analytics, ad impressions, clickstream, and event analytics. It can also work well for insurance event metrics if the model is denormalized properly.

# 5. Drill-down and roll-up capability

## Redshift

Redshift is excellent for drill-down and roll-up if you design a dimensional model.

Example:

```text
Region
  -> Agency
    -> Sub-agency
      -> Agent
```

You can build aggregate tables:

```sql
agg_daily_broker_metrics
------------------------
metric_date
region_name
market_category_name
agency_name
subagency_name
agent_name
applications
renewals
commission_amount
```

Then dashboards can drill:

```sql
SELECT agency_name, SUM(applications)
FROM agg_daily_broker_metrics
WHERE region_name = 'West'
GROUP BY agency_name;
```

Redshift is very strong here because:

- SQL is mature
- BI tools understand it well
- Hierarchies are easy to manage
- Aggregations are straightforward
- Historical analysis is natural

---

## MongoDB

MongoDB can support drill-down, but usually through:

```text
Precomputed summary collections
Application-level aggregation
MongoDB Charts
Custom API layer
```

Example summary document:

```json
{
  "metricDate": ISODate("2026-08-06T00:00:00Z"),
  "region": "West",
  "agency": "Agency 101",
  "subAgency": "Sub-agency 205",
  "agent": "John Smith",
  "marketCategory": "Commercial Lines",
  "applications": 12,
  "renewals": 8,
  "commission": 14500
}
```

MongoDB can be fast for dashboards if you precompute summaries.

But for complex analytical drill-down, it is usually less convenient than Redshift.

---

## Apache Pinot

Pinot is very good at dimensional drill-down when the data is denormalized.

Example event record:

```json
{
  "eventTime": "2026-08-06T10:15:00Z",
  "eventType": "APPLICATION_SUBMITTED",
  "applicationId": "APP-1001",
  "region": "West",
  "marketCategory": "Commercial Lines",
  "agencyId": "AG-101",
  "subagencyId": "SUB-205",
  "agentId": "AGT-300",
  "applicationCount": 1,
  "estimatedPremium": 12500,
  "commissionAmount": 0
}
```

Then you can query:

```sql
SELECT
    agencyId,
    SUM(applicationCount)
FROM broker_events
WHERE region = 'West'
GROUP BY agencyId;
```

Pinot can make this very fast using:

- Indexes
- Partitioning
- Star-tree pre-aggregation
- Streaming ingestion
- Real-time tables

However, you usually need to denormalize the data before loading it into Pinot.

That means instead of joining:

```text
fact_applications
dim_agent
dim_subagency
dim_agency
dim_region
dim_market_category
```

you often enrich the event in a stream processor and store the dimension values directly in the Pinot record.

---

## Apache Druid

Druid is also good at drill-down and roll-up, especially when you aggregate at ingestion time.

Example Druid rollup dimensions:

```text
event_time
region
market_category
agency_id
subagency_id
agent_id
```

Metrics:

```text
application_count
renewal_count
commission_amount
estimated_premium
```

Then dashboards query:

```sql
SELECT
    agency_id,
    SUM(application_count)
FROM broker_events
WHERE region = 'West'
GROUP BY agency_id;
```

Druid is especially good when time is a primary dimension.

For insurance dashboards, this works well for:

```text
Applications per day
Renewals expiring per week
Commission earned per month
Pipeline by region and market category
```

# 7. Query latency and concurrency

This is one of the biggest differences.

## Redshift

Redshift is optimized for analytical queries, but not necessarily millisecond operational queries.

Good latency pattern:

```text
Aggregate table or materialized view
    -> dashboard query returns in sub-second to a few seconds
```

But direct queries against raw fact tables can be slower.

Redshift is good for:

```text
Internal dashboards
Management reporting
Analyst workloads
BI tools
```

It is usually not the best choice for:

```text
Embedded high-QPS analytics
Millisecond operational screens
Thousands of simultaneous user-facing dashboard queries
```

unless carefully architected.

---

## MongoDB

MongoDB is excellent for:

```text
Indexed point queries
User-specific operational screens
Low-latency document lookups
```

Example:

```javascript
db.applications.find({
  "agent.agentId": "AGT-300",
  "status": "In Progress"
})
```

This can be very fast.

But complex group-by analytics across large datasets may become slower unless you pre-aggregate.

---

## Pinot

Pinot is excellent for high-concurrency, low-latency analytical queries.

Example:

```sql
SELECT
    region,
    SUM(applicationCount)
FROM broker_events
WHERE eventTime >= '2026-08-06'
GROUP BY region;
```

Pinot can serve many concurrent queries quickly.

This makes it a strong choice for:

```text
Embedded broker dashboards
Agent-facing analytics
Customer-facing analytics
Operational dashboards
```

---

## Druid

Druid is also excellent for high-concurrency aggregation queries.

It is especially good when queries are time-based:

```sql
SELECT
    DATE_TRUNC('hour', __time) AS hour,
    region,
    SUM(application_count)
FROM broker_events
GROUP BY 1, 2;
```

This works well for operational monitoring dashboards.

# 8. Complex joins and business rules

This is where Redshift is usually strongest.

## Redshift

Redshift handles complex joins well.

Example:

```sql
SELECT
    h.region_name,
    h.agency_name,
    h.subagency_name,
    h.agent_name,
    SUM(f.commission_amount)
FROM fact_commissions f
JOIN dim_sales_hierarchy h
    ON f.sales_hierarchy_key = h.sales_hierarchy_key
JOIN dim_market_category m
    ON f.market_category_key = m.market_category_key
JOIN dim_date d
    ON f.transaction_date_key = d.date_key
GROUP BY
    h.region_name,
    h.agency_name,
    h.subagency_name,
    h.agent_name;
```

This is natural in Redshift.

---

## MongoDB

MongoDB can use `$lookup`, but large analytical joins are not its strength.

Usually, you either:

```text
Embed related data
Denormalize documents
Precompute summaries
Move analytics to another system
```

---

## Pinot

Pinot has limited join capability compared with a data warehouse.

Usually, you enrich data before ingestion.

Example:

```text
Kafka event
    -> Flink/Kafka Streams enrichment
        -> add agency name, sub-agency name, agent name, region
            -> load into Pinot
```

Pinot is not designed to be a complex transformational warehouse.

It is designed to serve fast queries over denormalized analytical tables.

---

## Druid

Druid also has limited join capability compared with Redshift.

Like Pinot, the common pattern is:

```text
Stream enrichment before ingestion
Denormalized datasource
Pre-aggregated rollups
```

Druid is not usually used as the system where you implement complex insurance business transformations.

# 9. Handling insurance business complexity

Insurance metrics are often more complicated than simple event analytics.

Examples:

```text
Commission splits
Commission reversals
Policy cancellations
Endorsements
Renewal attribution
Agent moves between agencies
Agency mergers
Market category reclassification
Historical corrections
Finance reconciliation
Carrier statement adjustments
```

## Redshift

Redshift is usually best for this type of complexity.

You can implement:

```text
Slowly changing dimensions
Effective-dated hierarchies
Commission allocation facts
Audit trails
Restatements
Financial reconciliation
```

This is very important for commission dashboards.

---

## MongoDB

MongoDB can store this data, but complex analytical restatements are harder to manage cleanly.

It can work if the application logic handles it carefully.

---

## Pinot

Pinot supports real-time updates and upserts, but it is still not as flexible as a warehouse for complex restatements.

You need to design carefully:

```text
Use correction events
Use upserts for latest state
Enrich hierarchy at event time
Maintain immutable audit events separately
```

Pinot can support real-time commission dashboards, but finance-grade accuracy may still need Redshift.

---

## Druid

Druid is often append-oriented.

Corrections can be handled by:

```text
Negative events
Replacement segments
Reindexing
Compaction
Careful event design
```

But this is less natural than SQL-based updates in a warehouse.

For finance-grade commission reporting, Druid alone is usually not ideal.

# 11. Example drill-down query pattern

For all systems, the dashboard drill-down pattern can be similar.

## Level 1: Region

```sql
SELECT
    region,
    SUM(application_count)
FROM broker_metrics
WHERE event_time >= CURRENT_DATE
GROUP BY region;
```

## Level 2: Agency

```sql
SELECT
    agency_id,
    SUM(application_count)
FROM broker_metrics
WHERE event_time >= CURRENT_DATE
  AND region = 'West'
GROUP BY agency_id;
```

## Level 3: Sub-agency

```sql
SELECT
    subagency_id,
    SUM(application_count)
FROM broker_metrics
WHERE event_time >= CURRENT_DATE
  AND region = 'West'
  AND agency_id = 'AG-101'
GROUP BY subagency_id;
```

## Level 4: Agent

```sql
SELECT
    agent_id,
    SUM(application_count)
FROM broker_metrics
WHERE event_time >= CURRENT_DATE
  AND region = 'West'
  AND agency_id = 'AG-101'
  AND subagency_id = 'SUB-205'
GROUP BY agent_id;
```

The difference is not the query pattern. The difference is how each system performs and how easy it is to govern the data.
