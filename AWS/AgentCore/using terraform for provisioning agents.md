Yes, **Terraform is fully supported** for building and deploying Amazon Bedrock AgentCore infrastructure. 

When Amazon Bedrock AgentCore reached General Availability (GA) in late 2025, AWS explicitly announced support for AWS CloudFormation and resource tagging. Because Terraform’s official AWS provider (`hashicorp/terraform-provider-aws`) maps directly to the underlying AWS APIs and CloudFormation resource types, you can manage your entire AgentCore footprint using Terraform.

For enterprise environments in healthcare and insurance, where Infrastructure-as-Code (IaC), state management, and policy-as-code (e.g., Open Policy Agent) are mandatory, Terraform is the ideal tool. 

Here is how you leverage Terraform with AgentCore, including the critical distinction between provisioning infrastructure and deploying agent code.

---

### 1. Provisioning AgentCore Infrastructure via Terraform
You use the standard `hashicorp/terraform-provider-aws` to define your AgentCore resources. This allows your platform engineering team to manage the "plumbing" of your AI architecture declaratively.

Key Terraform resources you will use include:
* **`aws_bedrockagentcore_runtime`**: Provisions the serverless runtime endpoint, configures VPC/PrivateLink settings for network isolation, and assigns the IAM execution role.
* **`aws_bedrockagentcore_gateway`**: Creates the secure AI gateway, configures the authorizer (e.g., pointing to Amazon Cognito or an external OIDC provider), and attaches Lambda interceptors for custom pre-routing logic.
* **`aws_bedrockagentcore_gateway_target`**: Registers your internal APIs (OpenAPI specs), Lambda functions, or MCP servers as tools within the Gateway.
* **`aws_bedrockagentcore_memory`**: Configures the memory strategies (Semantic, Summary, User Preference) and retention policies for your agents.
* **`aws_bedrockagentcore_policy`**: Deploys your Cedar-based authorization policies to enforce deterministic guardrails at the Gateway level.

### 2. Separation of Concerns: Infrastructure vs. Agent Code
In an enterprise CI/CD pipeline, it is a best practice to separate **Infrastructure Provisioning** (Terraform) from **Agent Code Deployment** (CI/CD).

* **Terraform's Job (The "House"):** Terraform creates the AgentCore Runtime endpoint, sets up the ECR (Elastic Container Registry) repository, configures the IAM roles with least-privilege access to S3/DynamoDB, and establishes the PrivateLink endpoints to your internal EHR/claims systems.
* **CI/CD's Job (The "Tenant"):** Your GitHub Actions, GitLab CI, or Jenkins pipeline builds the agent code (ZIP or Docker container), pushes the container image to the ECR repository created by Terraform, and then calls the AWS API (via AWS CLI or AgentCore CLI) to update the Runtime endpoint with the new image URI or ZIP file.

*Note: While Terraform can technically trigger code deployments using `null_resource` or external data sources, relying on your standard container deployment pipelines to update the image URI in the AgentCore Runtime is much faster and aligns with standard DevSecOps practices.*

### 3. Alternative: CDK for Terraform (CDKTF)
AWS provides the **AgentCore CLI** (`@aws/agentcore`), which is designed to rapidly scaffold agent projects and automatically generate **AWS CDK (Cloud Development Kit)** code for the underlying infrastructure.

If your enterprise developers prefer writing infrastructure in TypeScript/Python using CDK, but your operations team strictly requires **Terraform** for state management and deployment, you can use **CDK for Terraform (CDKTF)**. 
* CDKTF allows you to take the CDK constructs generated by the AgentCore CLI and synthesize them directly into Terraform HCL (HashiCorp Configuration Language) or JSON. 
* This gives developers the "happy path" scaffolding of the AgentCore CLI while satisfying the enterprise mandate for Terraform.

### 4. Why Terraform is Critical for Healthcare & Insurance
Using Terraform for AgentCore unlocks several enterprise-grade governance capabilities:
* **Policy-as-Code:** You can use tools like Sentinel (Terraform Cloud) or OPA to enforce rules before deployment. For example, a policy can block the Terraform `plan` if a developer attempts to create an AgentCore Runtime without attaching a specific KMS key for encryption at rest, or if the Gateway is not configured with a VPC endpoint.
* **Multi-Account / Multi-Region DR:** Healthcare enterprises often separate workloads across multiple AWS accounts (e.g., Dev, Test, Prod, or separate accounts for PHI vs. non-PHI). Terraform workspaces or Terragrunt make it easy to deploy identical AgentCore architectures across these boundaries.
* **Auditability and State Locking:** Terraform state files provide a clear, version-controlled history of exactly which Cedar policies, Gateway targets, and IAM roles are active in your production environment, which is invaluable during HIPAA or SOC2 compliance audits.

### Summary Recommendation
Yes, you can and should use Terraform. Use the **`hashicorp/terraform-provider-aws`** to provision the AgentCore Runtimes, Gateways, Memory, and Identity configurations. Let your standard CI/CD pipelines handle the actual deployment of the agent code (ZIP/Containers) to those Terraform-managed endpoints. This provides the perfect balance of developer velocity and enterprise security governance.
