To incorporate your hierarchical agency data, you must inject the broker hierarchy into the pipeline before processing the metrics. Because the hierarchy lives in a separate system, you have two primary architectural choices: Dynamic Synchronization (Lookup) or On-the-Fly API Injection.
For a dashboard that requires maximum performance and flexibility, Option 1 (On-the-Fly API Injection) is highly recommended.
------------------------------
## Option 1: On-the-Fly API Injection (Recommended)
Since the hierarchy data is external, your backend API should fetch the hierarchy tree first, extract all relevant broker IDs under the user's scope, and inject them straight into the MongoDB $match stage. This avoids complex cross-system database joins. [1, 2] 
## How it works in your Backend API:

   1. Identify the logged-in user: A user logs in (e.g., a "Large Agency" manager).
   2. Query the External Hierarchy System: Fetch all sub-agencies and individual brokers belonging to that manager.
   3. Flatten into an Array: Create an array of all downstream broker IDs (e.g., ["BROKER_1", "BROKER_2", "BROKER_3"]).
   4. Execute MongoDB Query: Use the $in operator in your initial filter. [3, 4] 

## Updated MongoDB Pipeline:

db.applications.aggregate([
  {
    $match: {
      // Injected array of all broker IDs this user has permission to see
      brokerId: { $in: ["BROKER_1", "BROKER_2", "BROKER_3", "BROKER_4"] }, 
      
      // Active UI dropdown filters
      // state: "TX"
    }
  },
  {
    $facet: {
      "totalMatching": [{ $count: "count" }],
      "byState": [
        { $group: { _id: "$state", count: { $sum: 1 } } }
      ],
      // New Facet: Breakdown metrics by individual Broker / Sub-Agency
      "byBroker": [
        { $group: { _id: "$brokerId", count: { $sum: 1 } } },
        { $sort: { count: -1 } }
      ]
    }
  }
])

Your backend then maps the resulting brokerId fields back to their human-readable Agency names from your external system before sending the final payload to the frontend.
------------------------------
## Option 2: Sync and Database Join ($lookup)
If you sync your hierarchy data into a separate MongoDB collection (e.g., broker_hierarchy), you can use a $lookup join.
This approach is best if you want to let users filter directly by "Large Agency" or "Sub-agency" dropdowns without pulling massive lists of IDs from an external API every time.

db.applications.aggregate([
  // 1. Initial filter for basic dropdowns (State, County)
  {
    $match: {
      // state: "TX"
    }
  },

  // 2. Join with the hierarchy collection based on the brokerId
  {
    $lookup: {
      from: "broker_hierarchy",
      localField: "brokerId",
      foreignField: "brokerId",
      as: "hierarchyInfo"
    }
  },

  // 3. Flatten the joined array
  { $unwind: "$hierarchyInfo" },

  // 4. Security / Scope Filter: Ensure the logged-in user only sees their branch
  // Example: If a Sub-Agency manager logs in, match their subAgencyId
  {
    $match: {
      "hierarchyInfo.largeAgencyId": "LARGE_AGENCY_ABC" 
      // Or "hierarchyInfo.subAgencyId": "SUB_AGENCY_XYZ" depending on who logs in
    }
  },

  // 5. Run Facets, now with access to hierarchy fields
  {
    $facet: {
      "totalMatching": [{ $count: "count" }],
      
      // Breakdown by Large Agency
      "byLargeAgency": [
        { $group: { _id: "$hierarchyInfo.largeAgencyName", count: { $sum: 1 } } }
      ],

      // Breakdown by Sub-Agency
      "bySubAgency": [
        { $group: { _id: "$hierarchyInfo.subAgencyName", count: { $sum: 1 } } }
      ],

      // Standard dropdown metrics
      "byState": [
        { $group: { _id: "$state", count: { $sum: 1 } } }
      ]
    }
  }
])

------------------------------
## Performance Warning for Option 2
Using $lookup (Option 2) before a $facet stage prevents MongoDB from utilizing standard collection indexes effectively across the join. If your applications collection scales to millions of records, Option 2 will cause heavy memory usage and slowdowns.
Stick to Option 1 if your external system has a fast API to resolve the hierarchy tree into an array of IDs.
To help pinpoint the best option, how large is your applications collection (thousands or millions)? Also, how frequently does the broker hierarchy data change?
